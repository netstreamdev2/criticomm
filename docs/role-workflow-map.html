Who governs, who operates, who responds

A role is a set of responsibilities and access rules.
It is not always a person's rank or direct manager.

1 · Governance sets the boundaries

Super Admin

Platform and tenant setup; access and feature controls.

Web · platform scope
→

System Admin / Admin

Organisation users, roles, resources and configuration.

Web · organisation scope
Two boundaries: tenant = organisation; silo = department. Pages, actions and database policies must agree for a boundary to hold.
↓Sets up the people, equipment and access used by the operational desks below.

2 · Operations are parallel desks, not another admin ladder

System Controller

Cross-department command view: coverage, incidents, surveillance and operational systems.

Web · command / monitor

Department lead

Supervisor; Police Captain; FireChief / Chief. Plans duty and oversees the team.

Web + optional field app

Call and dispatch desks

Logger records calls; Dispatcher assigns units. ControlRoom / Operator can do both.

Web · work handoff, not rank

3 · Four field departments receive the work

Metro Police

Captain leads; Police / Officer / Metro and Security respond.

Field app important

Metro Fire

FireChief / Chief lead; Firefighter responds.

Field app important

Medical

Doctor and Paramedic are field roles. A distinct team-lead role is not defined.

Field app important

Disaster

Disaster responder is defined. A distinct team-lead role is not defined.

Field app important
Logger: may log a call; cannot use the dispatch queue or assign units.
Dispatcher: may work the queue; cannot use the call-intake route.
System Controller: operates modules; tenant, feature and access controls are excluded.
Field staff: receive assigned work; account and platform administration are separate.

Criticom · workflow map · 02 / 02

How work reaches a device and returns

Solid arrows show a handoff or data update.
The same person may cover more than one desk.

A · Incident workflow

Caller

Reports an emergency, location and contact details.

Outside the platform
→

Call intake

IncidentLogger captures the report. ControlRoom / Operator can also do this.

Creates incident record
→

Pending queue

The new incident waits for routing and a unit assignment.

Shared operational record
→

Dispatch desk

Dispatcher routes the call and assigns a unit. ControlRoom / Operator can also do this.

Updates incident + alerts crew
→

Field crew · mobile

Police, Fire, Medical or Disaster crew receives the job and updates its status.

Acknowledges / en route / on scene
Separate desks: Logger cannot dispatch; Dispatcher cannot log intake.Combined desk: ControlRoom or Operator can cover both jobs.

B · Duty and shift workflow

Department lead · web

Creates duty posts, assigns people for a date and publishes the board.

→

Shared records

Published roster, post, incident and status data connect web and mobile.

→

Field worker · app

Reads schedule; acknowledges duty; completes shift checks; receives and updates incidents.

App acknowledgements, on-duty status and incident updates return to supervisor / dispatch views

Case Manager

Reviews the incident record and closes cases after the operational response.

Viewer

Observes dashboards, incidents and reports. Intended as a read-oriented seat.

Mobile priority

Core for field responders; useful for Captain / Fire leadership when they also respond. Admin, intake, dispatch and controller work is mainly web.

Code reality: These arrows explain the intended workflow, not a guarantee that every data permission is complete. Route rules split intake from dispatch and server actions check some writes; tenant and silo isolation also depend on deployed database policies. Viewer write restrictions and cross-tenant behavior require a separate security audit. Mobile schedule refreshes on open / pull; a new duty publication is not confirmed as a device push alert.
