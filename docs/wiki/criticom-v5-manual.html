Volume I

The Platform

What Criticom is for, how it is put together, and the authorization model that makes one shared incident table safe for five separate emergency services.

Chapter 1

What Criticom Is

One call-taker logs an incident; the platform routes it to the right departments, puts it on a map, pushes it to the crews' phones, records everything they do at the scene, and keeps the evidential trail that an inquiry will read a year later.

1.1 The problem it solves

Five emergency services operate across eThekwini. They share a city, they share incidents, and they routinely need each other — a structure fire needs Fire and EMS and often Police for the cordon. What they did not share was a system: each kept its own records, so a call touching three services produced three partial accounts, joined only by the radio.

Criticom's premise is that the incident is the record and every department writes to the same one. Three properties follow:

  • Departments see their own work and no more — but when a call is routed to several, all of them see it. Resolved once, in the database.
  • The record is evidence. It gets read in disciplinary hearings, insurance disputes and inquests. A timestamp recording "when the network came back" rather than "when the crew arrived" is worse than none, because it looks authoritative.
  • Nothing may depend on good conditions. Coverage fails, phones lock, screens get ignored during a major incident. Each of those degrades rather than loses data.

Departments are silos in the code and database. The term names the isolation boundary, which is a security concept.

1.3 Lineage from V4

A rebuild of an ASP.NET MVC application of ~38 controllers over five SQL Server databases. V5 reproduces every capability and consolidates into one Postgres schema, with row-level security doing the separation the separate databases used to do badly. Five waves: 1–3 reached parity, 4 aligned a July feature drop, 5 added offline field operation, officer-down, automatic escalation, search, rate limiting and tests.

2.2 Logic in the database

Dispatching writes an incident row, updates unit state, appends a timeline entry, writes an audit record and raises one alert per receiving department. As application code that is six round trips that can half-succeed — and a half-dispatched call is a crew that never rolls. So those workflows are stored procedures, and web and mobile call the same one, so the two surfaces cannot drift.

The trade-off SQL is harder to test and harder for a TypeScript developer to change. It is accepted only where atomicity is the point. Reporting, KPI arithmetic and formatting stay in TypeScript, where they are readable and unit-tested.

2.3 Authorization in the database

Row-level security decides what each user reads and writes. The application never adds a WHERE silo = … for security — only to cut traffic. This is the most important decision in the system, and it is what makes a shared incidents table safe for five services. A bug in a page cannot leak another department's data, because the page never had it.

Chapter 3

Authorization

Two independent layers. The route matrix decides which screens a role may open. Row-level security decides which rows they may touch. The first is clarity; the second is the boundary.

3.1 Silos and helpers

Every user carries a silo and role in JWT app metadata. Three helpers read them — current_silo(), app_role(), is_global() — so a policy reads as the sentence a person would say.

A distinction worth keeping is_global() answers "may this role see across departments" and is right for SELECT; it returns true for read-only roles such as Viewer. Gating writes with it would grant those roles write access, so can_write_global() exists separately. Migration 0019 fixed five policies that had conflated the two.

3.2 The roles

The user_role enum has 25 values; 23 are assignable to people from Admin → Users. System is an internal service identity, and Citizen exists only for the public location-share flow, where a member of the public posts GPS against a single-use token and never holds an account.

The two-desk split

Call-taker and dispatch-desk groups barely overlap. An IncidentLogger may capture a call and may not work the queue; a Dispatcher may work the queue and may not capture calls. This mirrors how the control room is staffed, and it is pinned by tests — a regression merging the two desks would be an authorization change disguised as a convenience.

3.3 The route matrix

ROUTE_RULES is an ordered list of path prefixes with permitted roles and optionally a silo. canAccess() evaluates it, and it drives the middleware, the sidebar, the top navigation, the command palette and dashboard quick actions — so navigation and enforcement cannot drift. 

{ prefix: '/dispatch/log-call', roles: CALL_TAKER_ROLES },
{ prefix: '/dispatch',          roles: DISPATCH_DESK_ROLES },
{ prefix: '/police',            roles: [...POLICE_ROLES, ...ADMIN_ROLES], silo: 'MetroPolice' },
{ prefix: '/roster/mine',       roles: undefined },   // every role
{ prefix: '/search' },                                // every role; RLS scopes results

3.4 Row-level security

create policy incidents_read on public.incidents for select using (
  silo = public.current_silo()                       -- my department owns it
  or public.is_global()                              -- control room / admin
  or public.current_silo() = any(dispatched_silos)   -- routed to us
);

That third clause is what makes multi-department response work. Verified against live data: a paramedic searching returns the one call routed to Medical and not the police-only call beside it.

3.5 Privileged functions

Procedures that must bypass RLS run SECURITY DEFINER and open with a role check:

perform public.require_role('SystemAdmin','SuperAdmin','Admin','Dispatcher',
                            'Operator','ControlRoom','Supervisor','System');
Historic defect, now closed Before 0019 every mutating procedure was DEFINER with no role check and EXECUTE granted to anon: a caller with only the public anonymous key could route, dispatch or close any incident in any department, and the audit log would record it as legitimate with a null actor. 0019 added the guards; 0020 fixed revocations that were silently no-ops.

The deliberate exception: raise_panic() has no role gate. Any authenticated account may call for help. Gating an emergency on a role matrix is how somebody dies over a provisioning mistake.

Chapter 5

How a Request Works

5.1 Rendering a page

  1. Request hits middleware, which reads the session cookie and evaluates the route matrix. Unauthorized → /403. Unauthenticated → /login. Static assets are excluded, or the logo 404s.
  2. The (app) layout loads: session, operational settings, ops links, department branding. All four fail safe.
  3. The page (a server component) calls functions in @criticom/api with a server Supabase client carrying the user's cookies.
  4. Postgres applies RLS and returns only permitted rows.
  5. HTML is streamed. Client components — topbar, alert centre, assistant dock, maps — hydrate afterwards.

Every page is force-dynamic. Caching a page rendered for one operator's permitted view and serving it to another is exactly the failure this system cannot have.

5.2 Submitting a change

  1. A <form action={someAction}> posts to a server action.
  2. The action calls getSession() and re-checks the role. Never trust that the page was reachable — a form can be posted directly.
  3. It calls a function in @criticom/api, which either writes tables directly (RLS applies) or calls a stored procedure (guard applies).
  4. logAudit records it.
  5. revalidatePath refreshes the affected screens.

5.3 Realtime

Boards, timelines and the alert bell subscribe to Postgres change streams. RLS applies to the socket too, so a subscriber is only delivered rows they could have queried. Each subscription gets its own channel topic, because Supabase reuses a channel per topic and rejects listeners added after subscribe().

5.4 The offline path

  1. The responder acts. The operation is written to AsyncStorage with the time it was performed.
  2. The UI updates from the queue, not from the server — so the screen shows what was asked for.
  3. Delivery is attempted only when NetInfo reports the internet reachable.
  4. On success the entry is removed; on failure it backs off, and after eight connected failures it parks as failed and waits for a human.
  5. Handlers carry occurredAt, so the server records when the crew acted rather than when the network returned.

Why arrival is write-once arrived_timestamp is set only when it is null. Response-time KPIs and any inquiry into a bad outcome are computed from exactly that column, so a later status change — or a replayed offline update — must not be able to rewrite it.

Who may advance a status

update_responder_status() admits the responder roles plus supervisory and dispatch tiers. The forward ladder offered in the interface is Dispatched → En Route → Arrived → On Scene → Transporting → Resolved; one step at a time, because skipping states loses the timings the ladder exists to capture.

10.2 Shift routine

  1. Sign in. Check the top bar shows your department and the alert bell for anything outstanding.
  2. Open Dispatch → Log Incoming Call and leave it open. The intake clock starts when the screen opens, so a fresh screen per call keeps the timing honest.
  3. Take calls (10.3).
  4. Between calls, check Incidents for anything you logged that has not moved.
  5. At end of shift, confirm nothing you captured is still sitting in the queue unrouted, and hand over anything unusual verbally.

10.3 Tasks

Log an incoming call
Screen /dispatch/log-call  ·  Writes incidents, audit_logs  ·  Full procedure 22.1
  1. Capture Caller name and Contact as the caller gives them. Do not correct spelling later at the cost of listening.
  2. Enter the Call description / narrative — what is happening, in their words.
  3. Set the location: type the address and take a suggestion, or drop a pin on the map. The two stay in step; you do not need to type coordinates.
  4. Classify: incident type from the configured category tree, then Region and Incident severity.
  5. If casualties: Number of victims and, for EMS, the Medical severity code (P1 Red through P4 Blue). Tick EMS not required if it plainly is not a medical call.
  6. Watch for the duplicate warning. If it names an existing incident, stop and check before creating a second one.
  7. Choose the receiving departments if you are permitted to route; otherwise submit and the dispatch desk will.
  8. Submit. You get the incident number in a confirmation.
Afterwards The incident exists with a sequential number, your name stamped as call-taker, and — if routed — an alert on every screen in the receiving departments and a push to their phones.
Attach something to a call at intake
Screen /dispatch/log-call  ·  Writes incident_attachments, storage
  1. Use the attachment control before submitting.
  2. Submit as normal.
If the upload fails The incident is still created and you are told the attachment did not upload. Re-attach it from the incident page — the call is never lost to a failed file.
Ask a caller for their GPS position
Screen /incidents/[id]  ·  Needs BulkSMS configured  ·  Full procedure 22.5
  1. Open the incident.
  2. Enter the caller's mobile number in Contact citizen and submit.
  3. They receive an SMS with a single-use link. When they open it and allow location, the position lands on the incident.
Use when The caller cannot describe where they are — common on freeways and in informal settlements.

Chapter 11

Control Room Operator

ControlRoom · Operator

The full control-room desk: takes calls and dispatches. Global silo scope — sees every department.

11.1 Reach

Everything the call-taker reaches, plus the whole dispatch desk: /dispatch/pending, /dispatch/assign/[id], /dispatch/kpi, /dispatch/ptt, plus /disaster. Not the departmental report sections, and not /admin.

11.2 Shift routine

  1. Sign in and clear the alert bell — read anything raised overnight, including the morning digest.
  2. Open Dispatch → Pending Queue. The figure at the top is your queue depth; it is live.
  3. Work the queue oldest-and-worst first. Severity, then call time, is how it is already sorted.
  4. Take calls as they come (10.3), routing them yourself rather than leaving them queued.
  5. Watch for automatic escalations — an unassigned call raises a High alert at 10 minutes and a blocking Critical at 20.
  6. Check Dispatch → KPI before handover so you hand over a described state, not a surprise.

Route a call to departments

  2. Select every department that needs to attend. A structure fire is usually Fire and EMS; add Police if a cordon is needed.
  3. Add dispatch notes if there is something the crew must know before arriving.
  4. Confirm.

Chapter 12

Dispatcher

Dispatcher

The dispatch desk only. Works the queue, allocates units, watches the board. Does not take calls.

12.1 Reach

The dispatch desk (/dispatch/pending, /dispatch/assign/[id], /dispatch/kpi, /dispatch/ptt), incidents, reports, case management, cameras, hierarchy, roster allocation, leave, own performance. Not /dispatch/log-call — intake is the call-taker's desk.

Why you cannot log a call The two-desk split matches how the control room is staffed and keeps the operational KPIs meaningful: call-taker throughput and dispatcher throughput are separate measures, and they stop being measures if one person does both under one role.

12.2 Shift routine

  1. Sign in; clear the alert bell.
  2. Dispatch → Pending Queue is your screen for the shift. Leave it open — it is live.
  3. For each call: route to departments, then assign a unit.
  4. Watch the dashboard board for crews that have gone quiet — the engine will flag no-arrival after 30 minutes and silence after 4 hours, but you will usually see it first.
  5. Use the PTT console rather than a personal handset, so the traffic is logged.
  6. At handover, walk the incoming dispatcher through anything still open.

22.1 Log an incoming call

Log an incoming call
Screen /dispatch/log-call  ·  Who Admin tier, Operator, ControlRoom, IncidentLogger  ·  Procedure log_incoming_call()
  1. Open the screen fresh for each call. An intake clock starts on open and is shown as Time since call intake started. It turns amber then red at the thresholds set in Operations Settings.
  2. Caller name and contact number.
  3. Call description / narrative — what is happening.
  4. Location. Either type into the address field and pick a suggestion, or click the map. Address, Latitude and Longitude stay in step automatically. Add Suburb, City and Postal code where known.
  5. Classification. Pick the incident category and sub-category from the configured tree, then Region (Central, North, South, West, Outer).
  6. Incident severity — Low, Medium, High or Critical. This decides whether receiving crews get a corner toast or a blocking interrupt.
  7. Casualties, if any: Number of victims (1–5, 6-10, 10+) and Medical severity code (P1 Red Immediate, P2 Yellow Urgent, P3 Green Delayed, P4 Blue Expectant). Tick EMS not required when it is plainly not a medical call.
  8. Internal dispatch notes — anything the crew must know before arriving.
  9. Check the duplicate warning. If it names an existing incident, open it rather than creating a second.
  10. Receiving departments, if you may route. Selecting none files the incident under your own department for the dispatch desk to route.
  11. Submit.
Afterwards An incident row exists with a sequential INC-YYYYMMDD-NNNN number, status Pending Dispatch (or Pending Analysis for Disaster Management), your name as call-taker, and an audit row. 22.4 Handle a duplicate

Check for a duplicate
Automatic on the log-call screen  ·  Procedure check_duplicate_incident()

Chapter 32

Officer-Down

Call for emergency assistance
Control the SOS button, on every screen  ·  Procedure raise_panic()
  1. Press and hold the SOS button. It reads HOLD… and fills.
  2. The phone taps you at each third of the hold, so you can feel it arming without looking.
  3. After 2.5 seconds it fires. Release earlier and nothing happens.
  4. A confirmation tells you whether your position was captured.
What happens A Critical incident is created at your position and a blocking alert is raised to your own department and the control room. With no signal it is queued at the highest priority and sent the moment you have any. Position is raced against a four-second timeout — if no fix is available it sends anyway, marked position unknown.
Use the radio too The platform is a second channel, not a replacement. Raise it on the radio as well if you can.

If you trigger it accidentally: say so on the radio, and ask dispatch to close the incident with a note. There is no cancel — the button is deliberately easy to trigger and impossible to un-send, because hesitation is the worse failure.

Counted in Postgres because the console deploys serverless — an in-memory counter is per-instance, and ten concurrent functions would mean ten times the limit. It fails open If the limiter errors, the request proceeds. A rate limiter that takes down dispatch when the database hiccups causes more harm than the runaway loop it guards against.

If an operator hits a 429 in normal work, the limit is wrong, not the operator. Raise it in apps/web/lib/rate-limit.ts and deploy. To clear one person's counter: 

delete from rate_limit_buckets where key like 'chat:%<user-uuid>';

41.3 Responder app

eas build  --profile production --platform android   # native binary

eas update --branch  production --message "what changed"   # JavaScript only
The OTA trap — read before publishing an update An over-the-air update ships JavaScript only. If the new JavaScript imports a native module the installed binary does not contain, every handset crashes at launch. The defence is runtimeVersion, which follows the app version: bump the version whenever you add a native module, and older binaries become ineligible for the update instead of being handed something that cannot boot. Wave 5 added five native modules and moved the app to 1.1.0 for exactly this reason.

A phone is not receiving dispatchesProfile → Dispatch alerts states which of five cases applies (33.1). Realtime still delivers while the app is open in all of them.
"My update did not go through"The sync tray lists everything undelivered with its error. Queued work is held against that person's account and sends when they next have signal while signed in.
A panic fired by accidentClose the incident with a note. It is deliberately impossible to un-send.
Alert storm from a ruleDisable the rule from Admin → Automations, then inspect automation_events — repeat alerting means its claim key is wrong. Widening a threshold is the fast mitigation.
Automations not runningSee 37.4. Drive run_automations() from any external scheduler while cron is fixed.
Storage filling upScene photographs dominate. Nothing deletes them automatically, deliberately — they are evidence. Removing any is a records-retention decision.
Incident numbers look oddFormat is INC-YYYYMMDD-NNNN, sequential per department per day. Numbers before migration 0024 used a random suffix and are not sequential — history, not a fault.

43.3 Useful queries

-- Live officer emergencies
select incident_number, silo, responding_officer, location_address, incident_created_at
  from incidents
 where source = 'Responder-Panic' and status not in ('Closed','Resolved');

-- Calls waiting for a department right now
select incident_number, silo, incident_severity,
       round(extract(epoch from (now() - call_timestamp)) / 60) as minutes_waiting
  from incidents
 where status in ('New','Pending','Pending Dispatch','Pending Analysis')
 order by call_timestamp;

-- Automation health
select key, enabled, last_status, last_run_at, last_detail
  from automation_rules order by key;

-- Recent sign-ins
select user_name, silo, timestamp from audit_logs
 where action_type = 'Logon' order by timestamp desc limit 20;

Why the migration job matters A migration is the one artefact with no undo, and the sequence from nothing is what a new environment and a restore both execute. A migration that only works against the current production database has not been tested.

44.2 Testing

node --test with --experimental-strip-types. No framework, no transpile, no config — Node 22 runs the TypeScript directly. Imports use explicit .ts extensions.

SuitePins
roles.test.tsThe route matrix, including the two-desk split.
reporting/query.test.tsThat the report builder drops unknown columns, unsupported operators and invalid enum values.
automations.test.tsThat a zero threshold can never be stored.
outbox-policy.test.tsQueue ordering, collapsing, retry classification, ownership.
A pattern worth copying When safety-relevant logic is tangled with an untestable runtime, split the pure decisions into their own module and test that. outbox-policy.ts exists for this; outbox.ts re-exports it so no call site changed. Writing those tests immediately found a real defect — retry attempts were accruing while offline, so a crew in a tunnel would have a scene photograph marked failed.

44.3 Linting

pnpm lint runs biome lint, not biome check. The formatter disagrees with this codebase's consistent hand-formatting; running it produces a 150-file diff that changes no behaviour and buries every real finding. Rules the house style diverges from are off, each reviewed against its actual violations and recorded with count and reason in docs/07-ENGINEERING-STANDARDS.md.

44.4 Conventions

  • Server-action forms with uncontrolled fields.
  • Queries live in packages/api/src/<module>; pages never build queries inline.
  • logAudit on every mutation.
  • Prefer SECURITY INVOKER and let RLS scope; reach for DEFINER only where atomicity or cross-department writes demand it, and guard it.
  • Comments explain why, not what.
