Part I

What Criticom Is

Criticom is the command-and-control platform for eThekwini's emergency services. One call-taker logs an incident; the platform routes it to the right departments, puts it on a map, pushes it to the crews' phones, records everything they do at the scene, and keeps the evidential trail that an inquiry will read a year later.

1.1 The problem it solves

Five emergency services operate across eThekwini — Metro Police, Fire & Rescue, EMS, Disaster Management, and the central Control Room that fields the calls. They share a city, they share incidents, and they routinely need each other: a structure fire needs Fire and EMS and often Police for the cordon.

What they did not share was a system. Each department kept its own records, so a call that touched three services produced three partial accounts of it, and the only thing joining them was the radio. Criticom's premise is that the incident is the record, and every department writes to the same one.

Three properties follow from that, and they shape almost every design decision in this document:

  • Departments must see their own work and no more. A paramedic has no business reading a Metro Police case file. But when a call is routed to both, both must see it. That tension is resolved once, in the database, by row-level security — not per screen.
  • The record is evidence. Timestamps, who did what, which crew attended, what the scene looked like. These get read in disciplinary hearings, insurance disputes and inquests. A timestamp that records "when the network came back" rather than "when the crew arrived" is worse than no timestamp, because it looks authoritative.
  • Nothing may depend on good conditions. Coverage fails in basements and industrial areas. Phones lock. Screens get ignored during a major incident. The platform is built so that each of those degrades rather than loses data.

1.2 The five departments

Departments are called silos throughout the codebase and the database. The term is deliberate: it names the isolation boundary, which is a security concept, not an organisational chart.

Until one is uploaded, the interface renders a monogram badge in that department's colours, so nothing looks unfinished.

1.3 Lineage from V4

Criticom V5 is a rebuild of Criticom V4, an ASP.NET MVC application of roughly 38 controllers backed by five separate SQL Server databases. V5 reproduces every V4 capability and consolidates the five databases into one Postgres schema with row-level security doing the separation the separate databases used to do badly.

The migration ran in five waves. Waves 1–3 reached functional parity; wave 4 aligned V5 with a July feature drop in V4; wave 5 — the subject of much of this document — added what a production emergency service needs that V4 never had: offline field operation, an officer-down path, automatic escalation, cross-module search, rate limiting and a test suite.

2.2 Technology choices and why

Logic in the database, not only in the app

Dispatching a call writes an incident row, updates unit state, appends a timeline entry, writes an audit record and raises one alert per receiving department. As application code that is six round trips that can half-succeed — and a half-dispatched call is a crew that never rolls.

So those workflows are stored procedures. route_incident(), dispatch_unit(), raise_panic(), update_responder_status() each do the whole job in one transaction. Web and mobile call the same procedure, so the two surfaces cannot drift.

The trade-off Logic in SQL is harder to test and harder for a TypeScript developer to change. It is accepted here only where atomicity is the point. Reporting, KPI arithmetic and formatting stay in TypeScript (packages/api), where they are readable and unit-tested.

Authorization in the database, never only in the app

Row-level security decides what each user can read and write. The application never adds a WHERE silo = … for security — only ever to reduce traffic. This is the single most important architectural decision in the system, and it is what makes a shared incidents table safe for five services.

Consequence A bug in a page cannot leak another department's data, because the page never had it. The database returned the rows that user was entitled to and nothing else.

Realtime over polling

Dispatch boards, incident timelines and the alert bell subscribe to Postgres change streams. RLS applies to the socket as well, so a subscriber is only ever delivered rows they could have queried.

Server-rendered, per request

Every console page is force-dynamic. Caching a page that renders one operator's permitted view and serving it to another is precisely the failure this system cannot have.

Part III

Authorization

Two independent layers. The route matrix decides which screens a role may open. Row-level security decides which rows they may touch. The first is convenience and clarity; the second is the actual boundary. Neither is trusted to do the other's job.

3.1 Silos

Every user carries a silo and a role in their JWT app metadata. Three database helpers read them: current_silo(), app_role() and is_global(). Policies are written in terms of those, so a policy reads as the sentence a person would say: your department's rows, plus anything dispatched to your department, plus everything if you are global.

A distinction worth keeping is_global() answers "may this role see across departments" and is correct for SELECT. It returns true for read-only roles such as Viewer. Using it to gate writes would grant those roles write access, so a separate can_write_global() exists for write policies. Migration 0019 fixed five policies that had conflated the two.

3.2 The roles

The user_role enum carries 25 values. 23 are assignable to people from Admin → Users. The two that are not: System is an internal service identity used by automated writes, and Citizen exists only for the public location-share flow, where a member of the public posts their GPS against a single-use token and never holds an account at all.

Roles are grouped in packages/db/src/roles.ts. Groups compose, so a rule is written once.

GroupMembers
ADMIN_ROLESSystemAdmin, SuperAdmin, Admin
SUPERVISORY_ROLESAdmin tier + Supervisor, Captain, Chief, FireChief, System
CALL_TAKER_ROLESAdmin tier + Operator, ControlRoom, IncidentLogger, System
DISPATCH_DESK_ROLESAdmin tier + Dispatcher, Operator, ControlRoom, Supervisor, System
RESPONDER_ROLESResponder, Police, Officer, Metro, Security, Captain, Firefighter, FireChief, Chief, Paramedic, Doctor, Disaster

MEDICAL_ROLESParamedic, Doctor

The two-desk split

CALL_TAKER_ROLES and DISPATCH_DESK_ROLES deliberately barely overlap. An IncidentLogger may capture a call and may not work the dispatch queue; a Dispatcher may work the queue and may not capture calls. This mirrors how the control room is actually staffed, and it is pinned by tests — a regression that merged the two desks would be an authorization change disguised as a convenience.

3.3 The route matrix

ROUTE_RULES is an ordered list of path prefixes with the roles (and optionally the silo) permitted to open them. canAccess(path, role, silo) evaluates it. One list drives:

  • The Next.js middleware, which redirects an unauthorized request to /403.
  • The sidebar and top navigation, which render only reachable destinations.
  • The command palette, which only offers pages the user may open.
  • Dashboard quick actions.

Because all four read the same list, navigation and enforcement cannot drift — the classic failure where a link exists to a page that then refuses to load. 

// Ordered: the first matching prefix wins, so specific rules precede general ones.
{ prefix: '/dispatch/log-call', roles: CALL_TAKER_ROLES },
{ prefix: '/dispatch',          roles: DISPATCH_DESK_ROLES },
{ prefix: '/police',            roles: [...POLICE_ROLES, ...ADMIN_ROLES], silo: 'MetroPolice' },
{ prefix: '/roster/mine',       roles: undefined },   // every role
{ prefix: '/search' },                                // every role; RLS scopes results

3.4 Row-level security

The standard read policy, and the shape most tables follow:

create policy incidents_read on public.incidents for select using (
  silo = public.current_silo()                 -- my department owns it
  or public.is_global()                        -- I am control room / admin
  or public.current_silo() = any(dispatched_silos)  -- it was routed to us
);

That third clause is what makes multi-department response work. A paramedic sees a Metro Police incident precisely when it was routed to EMS, and not otherwise. This was verified against live data during wave 5: searching as a paramedic returned the one call routed to Medical and not the police-only call beside it.

3.5 Privileged functions

Stored procedures that must bypass RLS run as SECURITY DEFINER. Every one of them opens with a role check: 

perform public.require_role('SystemAdmin','SuperAdmin','Admin','Dispatcher',
                            'Operator','ControlRoom','Supervisor','System');
Historic defect, now closed Before migration 0019, every mutating procedure was SECURITY DEFINER with no role check, and EXECUTE was granted to anon. A caller holding only the public anonymous key could route, dispatch or close any incident in any department — and the audit log would record it as legitimate with a null actor. 0019 added the guards; 0020 fixed the revocations, which had silently been no-ops.

The deliberate exception

raise_panic() has no role gate. Any authenticated account may call for help. Gating an emergency on a role matrix is how somebody dies over a provisioning mistake, and the reasoning is written into the migration so a future reviewer does not "fix" it.

Security invoker where possible

search_everything() reads across six tables and every department. It is SECURITY INVOKER, so RLS runs for the calling user on each branch. Making it DEFINER for speed would turn one search box into a cross-department data leak.

Part IV

The Console — Module by Module

Every operator-facing screen, what it is for, and the decisions behind it. Routes are given as paths; all of them sit under the authenticated (app) group unless noted.

4.1 Dashboard /dashboard

Role-aware. A dispatcher gets the live operations board — queue depth, active deployments, a map, an incident feed, SLA gauges. A responder gets their assigned calls and shift status. A supervisor gets headcount and approvals. An administrator gets system health.

The shell above it carries the ops command bar on every page: an external-resources tier (E-NATIS, CAS, PERSAL, FIREARM, FINES, TRACE, FORENSICS, RealPTT, FlightRadar, MarineTraffic) driven by OpsLink configuration records, plus an internal module tier filtered by the route matrix. Administrators repoint or add systems without a deployment; placeholders render dimmed until an endpoint is issued.

4.2 Call intake /dispatch/log-call

The primary call-taking screen. Caller details, description, classification driven by the configurable incident-category tree, location by address autocomplete or map pin, and the receiving departments.

  • Duplicate detection runs before submission — 12-hour window, by caller number and by location plus type.
  • Attribution stamps the call-taker, which is what the operational KPIs are computed from.
  • Geocoding goes through a server-side proxy (Photon primary, Nominatim fallback). Cloud egress ranges are frequently blocked by Nominatim, which is why the primary is Photon.
  • Categories come from command_records, so a service adds an incident type from Admin rather than by deployment.

4.5 Responder /responder · /shift/*

The console counterpart to the phone. Start of shift is a three-step gate — mental readiness declaration, vehicle selection, vehicle inspection — and it must be completed before a crew may take incidents.

Why the gate exists The mental check is a fitness-for-duty declaration (substance use, emotional regulation, reaction time) and the vehicle inspection is a roadworthiness record. Letting somebody answer a call before either exists means there is no record that they were fit to attend — which is exactly the record that matters after an incident goes wrong.

Operational tuning

Twelve knobs, each declaring its type, bounds, default and description in a catalogue (packages/api/src/settings). The admin page renders from the catalogue, so adding a knob is one entry there. Values are stored as overrides in app_settings, validated and clamped on both read and write, and every change is audited. If the table is unreachable the code defaults apply — a tuning problem can never take a screen down.

4.17 Criti /assistant

The assistant, available as a full page and as a dock on every route. It reads the live board — active incidents, queue, crews on duty, available units, today's KPIs — through the caller's own session, so RLS decides what it can see. It cannot surface a record the operator could not open themselves.

It also acts. The model emits action codes which the server validates and executes: [UPDATE_STATUS|…], [FILL_REPORT|…], [ROUTE_INCIDENT|…], [BROADCAST|…]. Status values, silos and fillable fields are whitelisted server-side, and every executed action is audited. Groq is the primary provider, Gemini the fallback.

4.18 Search New in wave 5

Finding a record used to mean knowing which screen it lived on. An operator holding a plate number, a case number or half a surname had to first decide whether that made it an incident, a vehicle, a person or a report. Under pressure that is the wrong order: you have the string, you want the record.

search_everything() unions six tables — incidents, personnel, fleet, police reports, fire reports, security reports — behind one query, wired into ⌘K alongside page navigation and into a shareable /search page.

Trigram, not full-text Postgres's text search tokenises and stems, which is right for prose and wrong for nearly everything an operator types: INC-20260804-0042, ND 123-456, PSV-8891. Those are identifiers, and to_tsvector mangles them, so a partial identifier matches nothing. pg_trgm matches substrings — exactly the "I only have part of it" case — and forgives a misspelt surname. GIN trigram indexes cover every searched column.

5.2 The duty gate

A responder may not take incidents until today's readiness flow is complete. The gate is enforced in the app shell: on opening, an unfinished flow routes to the Shift tab.

Two deliberate escapes. Profile stays reachable — somebody who fails the readiness check can never satisfy the gate, which is correct, but they must still be able to see who they are signed in as and sign out. A gate with no exit is a trap, not a control. And if the readiness check cannot be evaluated because the device is offline, the crew is let through: the server remains the record of truth, and stranding a crew behind a check we cannot run helps nobody.

5.3 The offline outbox New in wave 5

Coverage is not a solved problem. Basements, lift shafts, the industrial south, half the N3 corridor at peak. Previously a responder marking themselves On Scene in a dead zone got an error, and the update was dropped — pushing recovery onto the person with the least attention to spare, and losing the timestamp the incident record is later reconstructed from.

Now every field mutation is written to disk first and delivered afterwards. Three consequences follow:

PropertyWhy it matters
The recorded time is when the responder acted Operations carry their own occurredAt, and update_responder_status() accepts it — bounded to the last 12 hours and never in the future, so an honest offline timestamp is possible without opening a path to backdating. An arrival time that drifts by the length of a dead zone is evidence that misleads an inquiry.
Nothing is dropped silently An operation that exhausts its retries is parked as failed and stays visible in the sync tray until a human resolves it. A photograph of a scene cannot be retaken an hour later.
Replay is safe Delivery can be interrupted after the server committed but before the phone recorded that. Every handler tolerates running twice — status changes are assignments, notes carry a zero-width replay marker, attachments derive their storage path from the operation id and upsert, and a panic is idempotent on client_ref.

Ordering

If the phone gets three seconds of signal, those seconds must carry the emergency, not a queue of photographs. Delivery priority is: panic, then status changes (dispatch allocates crews off them), then position, then notes, then attachments — the largest and least time-critical.

Collapsing

Only position heartbeats collapse: five stale fixes tell dispatch nothing the newest does not, and replaying them would walk the marker backwards across the map on reconnect. Every other operation is a distinct event with its own evidential value and is never merged.

Ownership

Handsets are shared across shifts Queued work is scoped to the account that captured it. Without that, an update queued by the officer going off duty would be delivered under the session of whoever signed in next — attributing their action, and their position, to the wrong person in a record later read as evidence.

Retry policy

Exponential backoff capped at 60 seconds, eight attempts. Those attempts only accrue while the device has a connection — the flush loop refuses to run when offline. So eight failures means the server is rejecting the write, not that the crew drove through a tunnel. Errors that will never succeed (RLS denial, missing target, 401/403/404) are not retried at all.

5.4 Officer-down Safety-critical

Four constraints, in the order they mattered:

  1. Usable one-handed, without looking. One fixed target in the same place on every screen, large enough to hit blind.
  2. Cannot fire by accident. A panic pulls crews off other calls; a few pocket presses is how a service learns to ignore the alarm. Hence hold-to-activate for 2.5 seconds, with escalating haptics so the phone confirms it is arming even face-down in a pocket.
  3. Cannot depend on the network. The queue takes it immediately, at the highest priority.
  4. Cannot wait for GPS. A fix can take fifteen seconds indoors. The position is raced against a four-second timeout and sent without coordinates if necessary — dispatch would rather have "officer down, position unknown" now than a precise position later.

raise_panic() then creates a Critical incident at the officer's position, sourced Responder-Panic, and raises a blocking acknowledgement-required alert to both the officer's own department and the control room. The console shows a standing banner in the app shell until the incident closes — the blocking pop-up fires once, but an operator who acknowledged it and went back to the queue needs a reminder that a colleague is still calling for help.

Position unknown When no fix is available the incident is placed at the eThekwini city centre rather than at 0,0 — which is in the Gulf of Guinea and would put a marker in the ocean — and the address text says plainly that the position is unknown.

ChannelCoversBlind spot
Supabase realtimeEverything, instantly, while the app is open — the state a crew on shift is normally in.App closed or backgrounded.
Expo pushThe phone locked in a cab holster.Needs a native module, and FCM on Android.

The overlap is the point: either alone has a blind spot, and a missed dispatch is not a recoverable error. Duplicates are cheap by comparison and are deduplicated by alert id where the two meet. Additionally, when an alert arrives over realtime while the app is backgrounded, the device raises it as a local notification — the socket delivered it to a screen nobody is looking at.

The Android FCM contract

Build-time, not runtime Android remote push cannot work without a Firebase registration. Historically the app shipped expo-notifications without google-services.json and failed at launch — the worst outcome, because a responder with no app is worse off than a responder with no push. The dynamic Expo config now refuses to produce an Android build without the file, with an actionable message, unless CRITICOM_ALLOW_NO_PUSH=1 states that a realtime-only build is wanted deliberately.

Every expo-notifications call is additionally guarded, so a build without the native module degrades to realtime-only rather than crashing. The Profile screen reports which case applies in plain words — permission denied, no push in this build, emulator, or registration failed — because a supervisor checking a handset before a shift needs to know whether it will ring, and whether that is fixable there or a build fact.

Part VI

The Automation Engine

Everything Criticom did until wave 5 happened because a person did it. That is right for dispatching and wrong for noticing.

6.1 Why it exists

A call sitting unassigned for twenty minutes. A paramedic's licence lapsing next week. A duty nobody acknowledged. All three are knowable from data already in the database, and all three previously depended on somebody happening to look.

The engine lives entirely in Postgres. There is no worker process to deploy, monitor or restart, and the rules run in the same transaction boundary as the data they read.

TableRole
automation_rulesOne row per rule: enabled flag, interval, and a JSONB config holding its thresholds — so "escalate after 10 minutes" becomes 15 without a deployment.
automation_runsAppend-only log. Automations act on live data and raise alerts that pull crews around; when one misfires, "what did it do and when" must be answerable without reading code.
automation_eventsThe anti-spam ledger, and the most important table here.

6.2 The seven rules

RuleEveryWhat it does
Unassigned call escalation
sla_unassigned		5 min A call still waiting for a department raises a High alert at the warn threshold (default 10 min) and a Critical, blocking interrupt at the critical threshold (default 20 min) — to the owning department and to the control room.
No arrival recorded
sla_no_arrival		10 min Dispatched or En Route with no arrival after 30 minutes. Confirm the crew is actually moving.
Open incident gone quiet
stale_incidents		30 min An active incident with no timeline entry for 4 hours. Bucketed by day, so a genuinely long incident — a flood, a major fire — produces one nudge a day, not one every four hours.
Certification expiry
cert_expiry		12 h Warns at 30, 7 and 1 days. To the member, because it is their licence to renew, and to the department, because rostering somebody unqualified is the department's problem first.

6.3 Anti-spam

The constraint that shaped the design An alerting system that cries wolf is worse than none, because people stop reading it.

Every action is claimed against automation_events with a unique index on (rule_key, entity_id, bucket). A rule that runs every five minutes therefore alerts once per escalation tier, not every five minutes forever. 

if public.automation_claim('sla_unassigned', inc.id::text, 'critical') then
  -- raise the alert; this branch can only ever run once for this incident/tier
end if;

Verified against the seeded database: the first pass raised 44 alerts across seven rules; a second pass immediately afterwards raised none.

6.4 Scheduling and failure

One pg_cron job, criticom-automations, calls run_automations() every five minutes. Per-rule cadence is the rule's own interval, so adding or retiming a rule is an UPDATE, never a schedule change — and there is exactly one job to reason about when something misfires at 03:00.

Five minutes is chosen against the tightest rule: unassigned escalation warns at ten. A tick at half the shortest threshold bounds the lateness of an escalation at five minutes, inside the tolerance of a ten-minute SLA.

One broken rule must not stop the rest

Each rule runs inside its own exception block. A rule that throws records an error against itself and the loop continues. The alternative — one broken rule silently stopping SLA escalation — is precisely the failure that must not happen quietly. Its last_run_at still advances, so a rule that throws every time does not retry on every tick and bury the log in identical failures.

If the scheduler is not running

The engine is complete without pg_cron: anything with a clock can call run_automations(). Migration 0026 degrades to a notice rather than failing where the extension is unavailable, so a local or self-hosted environment is not blocked by a scheduler. Admin → Automations reports a stalled scheduler explicitly, because a page full of enabled rules that have not run in a day is worse than one that says so.

Two columns worth explaining

dispatched_silos is an array, and it is what makes multi-department response work: it appears in the RLS read policy, so adding a department to it grants that department visibility atomically with the routing decision.

client_ref is a device-generated UUID with a unique index. It exists so a replayed create — the offline outbox retrying after the network returned — returns the original row rather than raising a second emergency for the same event.

Incident numbering

A defect fixed in wave 5 Numbers were INC-<date>-<random 100–999> against a unique (silo, incident_number) constraint. That is 900 values per department per day, so by the birthday bound a department had roughly a 50% chance of a collision at 35 calls in a day and was essentially certain past 80 — and a collision surfaced as an exception thrown at a call-taker with a caller on the line. eThekwini runs well past that. Replaced with next_incident_number(), a per-department daily counter producing INC-YYYYMMDD-NNNN.

7.4 Migrations

28 numbered files, append-only. An applied migration is never edited — the next one is written instead. Each runs inside a transaction, so a failing statement rolls the whole file back and a half-applied migration is not a reachable state.

PostgREST and function overloads RPCs are resolved by argument name. Adding a parameter with a default to an existing function creates a second overload, and a call matching both resolves to neither. The old arity must be dropped in the same migration — as 0024 does for update_responder_status and log_incoming_call.

8.2 The proxy pattern

No third-party key ever reaches a client bundle. Every external call goes through a server route under /api/external/* which holds the key server-side, requires an authenticated session, and is rate limited.

Each proxy degrades gracefully: with no key configured it returns a clear "not configured" response rather than erroring or, worse, returning fabricated data. A control room must be able to tell "this feed is switched off" from "this feed says there is nothing there". 

const { deny } = await requireAuth('external');   // 401 or 429
if (deny) return deny;
const key = process.env.TOMTOM_API_KEY;
if (!key) return unconfigured('TomTom traffic', 'TOMTOM_API_KEY');

8.3 CCTV cut-over

/api/cctv/cameras serves the SANRAL registry until the Hikvision integration is enabled with an app key, secret and base URL — at which point the same endpoint serves the live HikCentral estate. The cut-over is a toggle in Admin, not a deployment.

/api/cctv/stream brokers AK/SK-signed live-preview and recorded-playback URLs. Signing happens server-side only, and every grant is written to the audit log for chain of custody — footage retrieval is evidence handling, and who requested what has to be answerable.

Known CSP loosening script-src permits 'unsafe-inline' and 'unsafe-eval' for Next's inline bootstrap, and style-src permits 'unsafe-inline' for Tailwind's runtime theme variables and per-department inline colours. Tightening this needs per-request nonces, which is a separate piece of work.

9.3 Rate limiting New in wave 5

Several routes spend money or third-party quota per call: the assistant, geocoding, the traffic and flight and vessel proxies, PDF rendering, RealPTT, CCTV stream grants. All are authenticated already, so this is not about anonymous abuse. It is about the two things that actually happen to a running service — a bug that fires the assistant on every render and burns a month's model budget in an afternoon, and a console left unlocked in a control room, where the realistic damage is quota rather than data.

BucketLimitRationale
chat40 / minA person types perhaps 6 a minute; a render loop types 600.
geocode120 / minFires per keystroke-batch on the address field, so it needs headroom.
external90 / minMetered upstreams; panels poll on a timer.
pdf20 / minEmbedding scene photographs is the most expensive request served.
ptt60 / minRadio traffic is bursty by nature.
cctv60 / minEach grant is audit-logged; a flood pollutes the trail.

Counted in Postgres, not in the process: the console deploys serverless, so an in-memory counter is per-instance and ten concurrent functions would mean ten times the intended limit — which is not a limit. Identity is taken from auth.uid() inside the database function rather than from a caller-supplied key, so a route handler cannot get it wrong and a caller cannot spend somebody else's budget or reset their own.

It fails open If the limiter itself errors, the request proceeds. A rate limiter that takes down dispatch when the database hiccups has caused far more harm than the runaway loop it was guarding against.

9.4 Audit

audit_logs records actor, department, action type, entity, and a human-readable detail line for every mutation. Logon events are recorded there too, which is what the operational KPI logon report is computed from. Case closures, stream grants, automation changes and manual automation runs all name a person.

9.5 Outstanding items

These are open and should be closed before or at handover
  • V4 leaked credentials. The previous system's BulkSMS token pair and Gemini key are present in that repository's source history — including a hardcoded token in its notifications controller. They must be revoked at the provider; rotating them in V5's environment is not sufficient, because the old values remain in V4's git history.
  • Setup-time credential exposure. The Supabase service-role key and database password were pasted into a chat transcript during provisioning and should be rotated.
  • CSP nonces. Removing 'unsafe-inline' and 'unsafe-eval' from script-src.
  • Accessibility. 19 tracked warnings, mostly form labels not programmatically associated with their inputs on the call-taking screen — a screen reader announces those fields with no name.

Operations

Before anything else Every procedure here is slower than the radio. If the platform is degraded and crews are waiting, put the control room on radio and paper, then fix the platform. Nothing in this part is more urgent than that.

10.1 Environments

Vercel, built from main. NEXT_PUBLIC_* values are inlined at build time, so an environment change needs a redeploy, not a restart.
Database
Supabase, region eu-west-1. The direct host is IPv6-only from some networks; CLI work goes through the session pooler.
Responder app
EAS. Channels: development, preview, production.

10.2 Deploying

Console

Push to main; CI must be green. Vercel builds the same commit.

Database

set -a && . ./.env && set +a
node scripts/apply-migration.mjs supabase/migrations/00NN_your_migration.sql

Apply migrations before the deployment that depends on them. The application tolerates a schema newer than the code far better than the reverse.

Responder app

eas build  --profile production --platform android   # native binary
eas update --branch  production --message "what changed"  # JavaScript only
An over-the-air update can only ever ship JavaScript Adding a native module — a new Expo package, a permission, anything in app.json or app.config.ts — requires a real build. Publishing an OTA whose JavaScript imports a native module the installed binary lacks crashes every handset at launch. The defence is runtimeVersion: it follows the app version, so bumping the version makes older binaries ineligible for the update rather than being handed something that cannot boot. Wave 5 added five native modules and bumped the app to 1.1.0 for exactly this reason.

10.3 Backup and recovery

Supabase takes automatic daily backups; point-in-time recovery depends on the plan — verify which you have before you need it. Take a manual snapshot before anything irreversible: 

pg_dump "$SUPABASE_DB_URL" --no-owner --no-acl -Fc -f criticom-$(date +%F).dump

Restore into a new project first and check it, then cut over. What a database restore does not bring back:

  • Storage — incident-media, avatars, department-logos. Evidence photographs live here, so a restore that ignores storage silently loses the attachments a case file references.
  • Accounts created since the snapshot — re-create with pnpm db:create-admin.
  • Push tokens — harmless; phones re-register on next launch.

10.4 First response

Work in this order. Each step rules something out.

Common situations

SituationResponse
A phone is not receiving dispatchesProfile → Dispatch alerts on the handset states which case applies: permission denied (fixable there), no push in this build (needs an FCM build), emulator, or registration failed. Realtime still delivers while the app is open in all four.

Engineering Standards

11.1 Continuous integration

Every push and pull request. All steps block merge.

StepCatches
pnpm lintDefect-class lint rules (see 11.3).
pnpm typecheckFour projects: db, api, web, mobile.
pnpm test47 tests across three packages.
pnpm buildThe production console build.
Migrations from emptyAll 28 migrations applied in order to a throwaway PostGIS database.
Why the migration job matters more than it looks A migration is the one artefact with no undo, and the sequence from nothing is exactly what a new environment and a restore-from-backup both execute. A migration that only works against the current production database has not been tested.

11.2 Testing

node --test with --experimental-strip-types. No framework, no transpile step, no configuration file — Node 22 runs the TypeScript directly. Tests import with explicit .ts extensions, which the loader requires and which Metro and tsc both resolve unchanged.

The tests exist where a silent regression is not a bad experience but a call that does not reach a crew:

SuitePins
roles.test.tsThe route matrix — the authorization boundary. Including the two-desk split.
reporting/query.test.tsThat the report builder drops unknown columns, unsupported operators and invalid enum values, and keeps sensitive datasets closed.
automations.test.tsThat a zero threshold can never be stored — zero means "escalate the instant a call is logged".
outbox-policy.test.tsQueue ordering, collapsing, retry classification and ownership. Every rule reachable only when the network is down.
A pattern worth copying When safety-relevant logic is tangled with an untestable runtime (React Native, a Supabase client), split the pure decisions into their own module and test that. outbox-policy.ts exists purely for this; outbox.ts re-exports it so no call site had to change. Writing those tests immediately found a real defect — retry attempts were accruing while the device was offline, so a crew driving through a tunnel would have a scene photograph marked failed.

11.3 Linting

pnpm lint runs biome lint, not biome check. check also enforces the formatter, which disagrees with this codebase's consistent hand-formatting; running it produces a 150-file diff that changes no behaviour and buries every real finding.

Rules the house style deliberately diverges from are off, each reviewed against its actual violations and recorded with the count and reason in docs/07-ENGINEERING-STANDARDS.md. What remains is enforced. Accessibility rules are warnings rather than errors — real defects, tracked for repair, to be promoted back to errors once fixed.

11.4 Conventions

  • Server-action forms with uncontrolled fields.
  • Queries live in packages/api/src/<module>; pages never build queries inline.
  • logAudit on every mutation.
  • Prefer SECURITY INVOKER and let RLS scope; reach for DEFINER only where atomicity or cross-department writes demand it, and guard it with require_role().
  • Comments explain why, not what. A comment restating the code is noise; a comment recording the constraint that produced the code is the most valuable thing in the file.
